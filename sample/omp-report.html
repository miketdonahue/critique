Gateway Migration — Technical Plan

Consolidating three ingress paths onto a single MCP gateway. Draft for review.

Executive summary

We propose migrating the legacy REST proxy, the gRPC bridge, and the websocket fan-out onto one gateway service. This removes two duplicated auth layers, cuts p99 latency, and gives us a single place to enforce rate limits and audit logging.

Reference config

The gateway is configured declaratively. A minimal route block looks like:

routes:
  - match: { host: "api.internal", prefix: "/v2" }
    upstream: mcp-gateway.svc:8443
    auth: { mode: mtls, audience: "gw" }
    rate_limit: { rpm: 6000, burst: 200 }

Open risks

  • Websocket session affinity during phase 3 is unproven at scale.
  • The legacy REST proxy sets a non-standard X-Legacy-Auth header some clients still depend on.
  • Rollback tooling assumes a single active ingress; needs an update before cutover.

Decision needed

Should phase 3 proceed before websocket affinity is load-tested, or do we split it out?
